# Call workflows

RingAround supports three request modes, all behind the existing account approval gate:

- **Find businesses:** discover providers near the service address and ask for pricing or availability. Existing drafts without a destination keep this mode.
- **Call a specific business:** supply a business name, international phone number, and information-gathering task. The normalized number and business name are recorded with the request. The call-reporting endpoint rejects an alternative destination. The request has a one-business cap.
- **Research and call me:** research a task and call the signed-in user's saved profile number with the findings. The server resolves the destination from the stored profile; it never trusts a callback destination supplied by the browser. The number must have a country code. It can be updated and saved in the request form. This is a task callback, not a scheduled reminder.

All modes show a review before submission. Approved accounts start the agent after submission. Appointment commitments, account changes, payments, scheduled reminder triggers, and call transfers are not implemented or authorized by these request modes.

## Call progress

The authenticated `report_call` MCP tool accepts optional `summary` (1,000 characters) and `transcript_excerpt` (8,000 characters). These are factual reports from the calling agent's monitored transcript. They are not generated by a separate summarization model, and the UI does not claim to stream live audio. The latest summary and cumulative transcript excerpt are stored per business, shown on the request page, and refreshed while the agent works. Old agents that send only `detail` preserve any previously stored summary and excerpt.

The existing `quoted` status is retained for database compatibility. Direct calls and requester callbacks display it as **Result**, including useful answers without a price. The agent skill specifies the reporting contract and prohibits fabricated dialogue.

## Follow-up instructions

Messages use the existing Managed Agents `user.message` endpoint, which can continue an idle session. The response's event ID is returned to the client. The UI shows **queued** until the event is reported with `processed_at`, then **received by the agent**. It keeps polling while messages are queued, even when the session is idle. Duplicate queued/processed event versions are merged. Receipt means the agent consumed the instruction; it does not guarantee the requested action succeeded.

The updated calling skill explicitly tells the agent to reassess follow-up instructions in the same session, including new information about a business's 24/7 opening hours. It must explain specific restrictions rather than silently requiring a new request. No automatic interruption is sent: interrupting a supervisor during a live call could leave that call unattended.

## Deployment and validation

Apply additive migrations `0003_call_progress.sql` and `0004_direct_call_destination.sql` before serving the new code. The existing production deployment workflow applies migrations and uploads the updated `skills/ringaround/SKILL.md`; PR previews do not update the shared calling agent. Existing managed sessions retain their original skill configuration. New sessions should be used to validate the updated agent instructions.

Run `npm test` for destination validation and event-acknowledgement regression tests. Full voice execution still needs a controlled test with the configured telephony tools after deployment. A local mocked API can verify request creation, MCP reporting, transcript rendering, and follow-up receipt without placing calls or spending API credits.
